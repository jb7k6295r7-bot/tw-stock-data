# 台股自有資料庫：讀取規則

`https://raw.githubusercontent.com/jb7k6295r7-bot/tw-stock-data/`

**完整契約與當前涵蓋範圍（列數、日期區間、各層現況）讀這一份**——它與資料同版本控管，
本文刻意不重複那些會過期的數字：

```
refs/heads/main/docs/READ_CONTRACT.md
```

★ 問「現在有什麼、缺什麼」讀 **`data/meta/_db_status.md`**（每日自動產生）；
問「最近一輪跑得好不好」讀 **`data/meta/_last_run.md`**。
這兩份比臨時拼查詢可靠，而且不會漏掉自己沒想到要查的那一項。

## Trigger

需要台股的**量化數字**時使用：個股歷史價量、全市場單日篩選、三大法人買賣超、
融資融券、本益比與股價淨值比、股本／發行股數、大盤指數與漲跌家數、興櫃成交、
停牌與處置注意。

**不要**在只需要消息面時觸發——資料庫裡沒有新聞。

## 零、界線：資料庫取代數字，不取代消息

- 量化欄位 → 讀資料庫
- **消息面 → 仍然走白名單搜尋 ＋ 14 天窗口 ＋ seen 帳本**

把消息面接上資料庫是**做不到**，不是「還沒做」。

### ⚠ 讀取方式的授權是專案綁定的

「不可用 Bash／curl 抓網頁繞過 WebFetch」的例外，是使用者針對**特定專案**放行的。
**其他專案要用 curl 讀這個 repo，必須另外取得使用者同意**，不可自行沿用。
**WebFetch 任何專案都可以用**，不需要額外授權。

## 一、四條路徑，用查詢的形狀決定

| 要回答什麼 | 讀哪裡 |
|---|---|
| 一檔的多年歷史 | `data/stocks/<代號>.csv` |
| 一天的全市場（篩選、排序） | `data/universe/daily/<日期>.csv` |
| 一檔的三大法人 | `data/stocks_inst/<代號>.csv` |
| **一檔的融資融券** | `data/stocks_margin/<代號>.csv` |
| **一檔的本益比／殖利率／股淨比** | `data/stocks_per/<代號>.csv` ⚠ 見陷阱 11 |
| **興櫃的歷史** | `data/universe/esb/<代號>.csv` |
| **停牌（暫停／恢復交易）** | `data/meta/suspend.csv` ⚠ 見陷阱 12 |
| **處置股** | `data/meta/disposal.csv` ⚠ 見陷阱 12 |
| **注意股** | `data/meta/attention.csv` ⚠ 見陷阱 12 |
| 當日速查（追蹤股） | `data/latest/<代號>_price.csv` 等 |

**用錯軸的代價很大**：拿日檔去湊一檔的歷史＝掃兩千多個檔、數百 MB。
反過來拿三千個個股檔做單日篩選也一樣慢。

### ★ 興櫃：看到一列不代表沒有歷史

**最容易誤判的一點。** 興櫃歷史在 `data/universe/esb/`，**不在 `data/stocks/`**——
同一檔在 esb 可能有數千列、在 stocks 只有一列。

成因：universe 日檔較晚才納入興櫃。兩邊欄位也不同——**興櫃官方只給高／低／均價，
沒有開盤與收盤**，硬合併等於憑空生出兩個價格欄，所以刻意分開存。

esb 的 `price_basis` 為 `無成交` 時，價格欄是**空的**（不是 0）。

### 權威來源：重複時誰贏

- **歷史與回測 → `data/stocks/`（唯一權威）**
- 當日速查 → `data/latest/`
- `data/history/` 與 `data/stocks/` 重疊但**由不同程式維護，會無聲飄移**；
  價格不要讀它，它剩下的價值只有尚未轉置的 `_revenue`

## 二、基準日：用讀的，不要推算

`data/latest/_manifest.json` 自己寫著：
**`date_max` 才是真正的資料基準日；`target_trading_day` 只是查詢用的猜測值。**

- **不要用執行環境的系統時鐘推論「今天應該有資料」**——沙箱時鐘實測差過一天。
- 抓取是**台北 19:00 與 23:59（週一～週五）**。**盤中讀到的一定是前一交易日收盤**，
  這不是錯，但報告要寫出來。
- 23:59 那班會**修正** 19:00 的錯漏，被改的列寫進 `data/_changes.log`。
  跨越那個時點的分析要重新對帳。

## 三、十三個讓答案靜默出錯的陷阱（都實測踩過）

**1. raw 的 404 會被 CDN 快取，而且 `?query` 破不掉。**
raw.githubusercontent **忽略未知的 query 參數**，所以 `?r=亂數` 完全無效。
→ 改用 **`refs/heads/main/...`** 路徑形式重試。

這是「查不到」三種情況裡最容易被誤記成「官方確實沒有」的那一種：
**還沒查／查過確實沒有／查法錯了**——第三種最常被誤記成第二種。

★ 2026-09-08 實際發生過：上櫃停牌猜了五個端點名全 404，就寫進文件說
「沒有來源、永遠補不回來」，還發信告訴別的線。實際上它在 `bulletin/sprcHis`（**POST**）。
**下「沒有來源」的結論之前，先去看官方頁面自己怎麼叫它。**
⚠ 而且**官方的頁面路徑與 API 路徑不一定對得起來**
（頁面 `announce/market/halt.html` ↔ API `bulletin/sprcHis`），
所以從頁名回推 API 名這條路本來就不通。

**2. 不要用 WebFetch 讀大 JSON。** 會被截斷，而且**被憑空補齊**，看起來像完整的。
要讀就讀 CSV。

**3. 檔案存在不等於欄位有值。** 例：股本檔的面額欄在來源端一律是空字串，
任何「面額 > 0 才執行」的分支都會被整段跳過。

**4. 「成交金額 ÷ 成交股數」不是均價。** 官方兩欄統計範圍不同（金額含盤後定價與鉅額交易，
高低只算盤中），約 **0.2%** 的股票隱含均價會落在當日高低之外。
要均價用高低中值或收盤。

**5. 產業別代碼有「兩層」，但公司層級只有子的那一層。**
`data/meta/industry.csv` 是**上市＋上櫃**的公司對應表（實測 1,094 ＋ 890 ＝ 1,984 檔），
裡面只有**子類股**代碼。母類股 **13 電子工業**與 **07 化學生技醫療**在這張表是 **0 檔**——
拿它們去比對，程式不會報錯，只會**一檔都不命中**，規則等於沒生效。

母類股不是正式產業別。證交所《上市公司產業類別劃分暨調整要點》第二點（最後修正 114.06.09）
列的是 **33 種平行類別**，全文沒有出現「電子工業」「化學生技醫療」；
這兩個名字只活在**每日收盤行情（`MI_INDEX type=13`）與類股指數**這兩個彙總層。
13 涵蓋 24～31 這八個子類、07 涵蓋 21 與 22，是從行情端點的成分**實測**出來的——
**沒有任何官方文字寫過這個層級關係**，引用時要標明是實測不是明文。

實務對照：

| 要做的事 | 用什麼 | 用錯會怎樣 |
|---|---|---|
| 排除生技醫療 | **22 生技醫療業**（實測 159 檔＝上市 61 ＋ 上櫃 98） | 用 07 → 0 檔，排除完全失效；而且用 07 的概念去手動擴充會連帶誤殺 21 化學工業 42 檔 |
| 排除金融保險 | **17**（葉節點、無子類，實測 40 檔） | 沒有層級問題 |
| 要「電子」這個概念 | **自己列舉 24～31** | 用 13 → 0 檔 |

**6. `sectors.csv` 的 `members` 只算上市，`industry.csv` 是上市＋上櫃。**
兩張表放在一起看會得到互相矛盾的家數：13 電子工業 sectors 宣告 **458**、industry.csv 實際 **909**；
07 宣告 **88**、實際 **201**。

更麻煩的是**有 8 個子類股連上市家數都對不上**（sectors 宣告 vs industry.csv 的上市數）：
17 金融保險 48 vs **31**（差 −17）、20 其他 58 vs 52、10 鋼鐵 32 vs 31、01 水泥 8 vs 7、
03 塑膠 22 vs 21、29 電子通路 23 vs 22、05 電機機械 49 vs **50**、22 生技醫療 60 vs **61**。
差異原因未查（可能是統計基準日不同，或含／不含特別股與 TDR）。

→ **規則、報告、skill 裡一律不要寫死家數，要用就從 `industry.csv` 現算**；
引用任何家數之前先問「含不含上櫃」。`sectors.csv` 只拿來查母子關係與名稱，**不拿來數**。

**7. 興櫃 363 檔完全沒有產業別。** `industry.csv` 只涵蓋上市與上櫃。
但這通常不需要另外解——興櫃本來就沒有開盤與收盤價（見上面「★ 興櫃」），
**技術面判讀在它身上整套不成立**，缺產業別只是表面症狀。
處理方式是把興櫃排除在篩選母體之外，不是為它放寬規則。

**8. 大盤的 `change_pct` 欄沒有正負號。**
`data/latest/market_index.csv` 的四欄是 `date, close, change, change_pct`——
**`change` 帶號，`change_pct` 不帶號**。實測：2026-09-02 `change` 是 `-784.0`、
`change_pct` 寫 `1.67`；2026-09-03 `change` 是 `-307.06`、`change_pct` 寫 `0.67`。

→ **方向一律由 `change` 的正負號判定，不可直接拿 `change_pct` 從字面讀。**
直接讀會把「跌 0.67%」寫成「漲 0.67%」，**而且不會報錯、數字本身也完全合理**。
漲跌家數（`market_breadth.csv`）與成交金額（`market_amount.csv`）沒有這個問題。

**9. `data/latest/<代號>_price.csv` 只有最後 300 列。**
這是「當日速查」用的截斷檔，不是完整序列。**拿它算 240MA 只剩約 60 根可用**，
年線與年線方向都會失真，而且**不會報錯**——均線照樣算得出來，只是樣本不夠。

→ **要長序列（季線、年線、扣抵、OBV 60 日、型態偵測、回測）一律讀 `data/stocks/<代號>.csv`**
（實測 3017 有 2,845 列）。`data/latest/` 只用來看當日收盤與最近幾天。
**也不要改讀 `data/history/`**——見上方「權威來源」，那一支會無聲飄移。

報告裡寫出來的日K根數（例「日K 406 根」）就是這件事的自檢點：
**根數剛好是 300 就要懷疑自己讀錯檔了。**

**10. `data/universe/daily/` 只收「當天有成交」的證券。**
實測 2018-12-22／2018-11-05／2022-10-28／2026-09-04 四天、上市＋上櫃共 7,890 列，
**`volume == 0` 的列一列都沒有**，最小成交量永遠 ≥ 100 股。

→ 某檔在某個交易日**沒有那一列 ≠ 漏抓**，是**那天它沒有成交**——
可能是無成交（冷門股），也可能是停牌（全額交割、重大訊息、減資換發新股）。
全庫這樣的缺漏共 **50,922 段**
（2026-09-07 稽核，最集中的日子落在 2018 Q4 與 2022 Q4 兩段空頭）。

→ **任何假設「每個交易日每檔都有一列」的計算都會錯**：均線、扣抵值、OBV、ATR、
周轉率、法人連續買賣超天數。

★ **上市與上櫃現在都分得出「無成交」與「停牌」**（`data/meta/suspend.csv`，
上市 2011-10-03 起、上櫃 2011 起）。
⛔ 本文 2026-09-07 版曾寫「上櫃分不出、只能從 2026-09-07 起累積」——**那是錯的，已更正**。

★ **判讀方法 2026-09-07 已由 K線分析線裁定**，權威版本在跨線信箱的
`00-必讀-乙3-K線線.md` 必守第 6 條。資料庫這一側只提供兩件事：

- **拿來比對的交易日曆是 `data/meta/calendar_twse.csv`**（2,845 天，來自大盤層級的
  TWSE `FMTQIK`，與建日檔的個股端點不同條路）。⚠ 不要用 `daily/` 的檔名集合或
  `_coverage_*.csv` 當日曆——見第六節第 2 項，那兩個都是循環自證。
- **停牌要查 `suspend.csv`**，不要拿日檔有沒有那一列去推。

⛔ 資料庫線**不代為決定**要補值、跳過還是縮短視窗，也不要把那邊的門檻抄進本文
（抄過來就是第二份權威，它會跟原版飄移）。

**11. `data/stocks_per/` 的 `close` 與 `fs_quarter` 兩欄，上市與上櫃長得不一樣。**

這一層 2026-09-07 才從日檔轉置出來，**來源端本身就不一致，轉置只是原樣搬過來**。
8 檔抽驗（上市 2330／2317／1101／2454，上櫃 8299／6488／3105／5274）結果完全一致：

| 欄 | 上市 | 上櫃 |
|---|---|---|
| `close` | 2017-04-15 起才有（之前 551 列空白）| **全期空白**（2,845 列全空）|
| `fs_quarter` | 格式 `115/2`，2017-04-15 起 | 格式 **`115Q2`**，**2025-01-02 起**（之前 2,439 列全空）|

→ **`close` 不要當價格用**，價格一律讀 `data/stocks/`。這一欄留著只是為了跟來源逐欄對得起來。

→ ⛔ **`fs_quarter` 只寫 `(\d+)/(\d)` 這一種解析式，上櫃會一列都 parse 不到**——
而且**不會報錯**，只會安靜地變成「這檔查不到財報期別」。
判斷「手上這期 EPS 過期了沒」就是靠這個欄位。
**兩種都要收**：`^(\d{2,3})[/Q](\d)$`，或先 `.replace("Q", "/")` 再解析。

⚠ 上櫃 2025 年以前**真的沒有這個欄位**——那不是解析失敗，是來源沒給。
兩者要分辨得出來，否則會把「來源沒有」誤記成「程式壞了」（見陷阱 1 的三種「查不到」）。

**12. 停牌／處置／注意這三個檔，九成是權證。**

三個檔都在 `data/meta/`，鍵是（代號＋日期）：

| 檔 | 日期欄 | 內容 | 區間 |
|---|---|---|---|
| `suspend.csv` | `halt_date`／`resume_date` | 暫停與恢復交易 | 上市 2011-10-03、上櫃 2011 起 |
| `disposal.csv` | `announce_date`／`start_date`／`end_date` | 處置期間、原因、累計次數 | 2010 起 |
| `attention.csv` | `date` | 注意原因、累計次數、當日收盤與本益比 | 2015 起 |

→ ⛔ **九成是權證，要用 `sec_kind` 過濾。**
停牌那 **10,034 列**的組成：**權證 9,594、普通股只有 409、興櫃 31**。
不過濾直接算「某年有幾檔停牌」會多出二十幾倍，**而且數字看起來完全合理**。
處置與注意也一樣混著權證與可轉換公司債（`33245 雙鴻五` 這種）。

⚠ `sec_kind` **優先用來源自己給的「有價證券類別」欄**（上櫃股票／權證／
轉交換公司債／興櫃-一般板），**代號形狀只當退路**。
理由：**興櫃的代號也是四位數字**，形狀規則會把興櫃判成普通股。
早期（約 2015 以前）那一欄是空的，那時才退回形狀規則。

→ ⛔ **處置要用區間判，不是公告日。** `announce_date` 與 `start_date ~ end_date`
是分開的三欄，處置期間通常晚於公告日一到數個營業日。
要問「某天這檔是不是在分盤撮合」，用 `start_date ~ end_date`；
拿公告日去判會把整段處置期間漏掉。

⚠ 這三個檔是**事件表**，不是逐日展開表。要「某檔某天的狀態」得自己展開區間。

⚠ 外部核對：官方 2015 那一頁自稱「證券個數 104、總累計次數 204」，
我方上櫃 2015 是 **102 檔、200 個事件**。差 2 檔 4 筆，**成因未查**。

**13. 面額變更會在還原報酬裡產生單筆 −95% 的假報酬，而且不會報錯。**

少數個股在歷史上做過**面額變更**（例如 10 元面額改為其他面額）。
那一天的收盤會出現一個**與股價無關的跳躍**——它是計價單位換了，不是漲跌。
`data/adj/` 的因子只涵蓋**除權息與減資**，**不涵蓋面額變更**，所以：

- 用還原價算長區間報酬時，那一筆會變成**單筆 −95% 這種量級的假報酬**
- **不會報錯**，因為每一欄的數字本身都合法
- 不是每天都會踩到，但**踩到時是靜默的**——它會直接污染整段區間的累積報酬

→ **判定規則：相鄰兩個交易日的收盤比 `close(t) / close(t-1)` 落在 `< 0.55` 或 `> 1.8`，
且 `data/adj/` 裡沒有對應日期的除權息或減資事件可以解釋，就當作疑似面額變更，
該筆單獨標記、不併入報酬序列。**

⚠ 兩個條件**要一起看**。只看比值會把正常的除權息與減資也掃進來（那些有因子、應該被還原）；
只看有沒有事件則完全抓不到面額變更（因子表裡本來就沒有它）。

⚠ 這條與第四節「不要為了消掉 mismatch 而擴充候選面額」是**兩件事**：
那一條講的是**股本表的靜態面額**（`資本額 ÷ 股數`，拿它比對常見面額是循環論證）；
這一條講的是**時間序列上的一次跳躍**，靠的是價格序列本身加上因子表的缺口，不是猜面額。

⚠ 出處與現況：本條於 **2026-09-08 由另一條線移交給資料庫線**（原本寫在那一支 skill 裡，
改成指路後若資料庫這側沒收，規則會變成兩邊都沒有）。
**門檻 0.55／1.8 與「約 26 筆」的量級沿用移交內容，資料庫線尚未自行複核那份名單。**
要把它變成管線裡的自動標記之前，先在 `data/stocks/` 全庫掃一次、把命中的逐筆看過，
並把結果寫進 `docs/READ_CONTRACT.md`。**在那之前這是判讀時的人工檢查，不是已驗證的資料欄位。**

## 四、必須揭露的限制（會改變結論）

- **`data/stocks/` 全部是未還原價**：除息日報酬被低估，高殖利率股最嚴重。
  **但現在可以自己還原**——`data/adj/` 有 **2,199 檔、19,385 個事件**
  （除權息 18,853 ＋ 減資 534），**上市與上櫃都有**。
  還原價 ＝ 原始價 × F(d)，F(d) 是 d **之後**所有事件的因子連乘；
  **最新價的 F 恆為 1（現價不動，只動歷史）**。詳見 `READ_CONTRACT.md`。
  ⚠ 上櫃因子來自 **FinMind**（TPEx 沒有歷史來源），引用時要揭露來源不同；
  已用上市那一半對 TWSE 官方全量核對過、不符 0.00%
  ⚠ **因子只涵蓋除權息與減資，不涵蓋面額變更**——見陷阱 13
- ~~三大法人只有上市（T86）：上櫃另有端點，未實作~~ ← **這條是錯的，2026-09-07 更正**。
  **上櫃法人早就實作了**：`otcinst` feed 覆蓋 2,845／2,845 天、抽驗 36,512 列 0 不符，
  `data/stocks_inst/` 是**上市＋上櫃合併**的 2,661 檔。
  ⚠ 照舊版寫法會對上櫃股說「沒有法人資料」，而**法人連續買超是選股的硬條件之一**——
  等於把上櫃股整批錯殺。
- **三大法人的起始年份比價格晚**：這是「還沒回補」不是端點限制，`--inst` 沒有日期下限
- **股本有少數檔對不起來**：DR（一單位對應的原股數不是 1）與代號帶 `*` 的非 10 元面額股，
  維持 mismatch 是刻意的，**不要為了消掉它們而擴充候選面額**——
  `資本額 ÷ 股數` 在兩欄都正確時**就等於面額**，再拿它比對「像不像常見面額」是循環論證。
  ⚠ 這是**靜態面額**的問題；**時間序列上的面額變更是另一件事**，見陷阱 13
- **上櫃有部分檔的股數與股本來自不同日期**：`shares` 取自每日更新的日檔，
  `capital` 取自較舊的基本資料快照，`note` 欄會寫明。**這不是錯誤**
  （可轉債轉換與員工認股讓股數持續長大）。算佔股本比重用 `shares`，
  **不要跨這兩欄相除去反推面額**

## 五、回測一定要用 first_seen／last_seen

`data/meta/stocks.csv` 有數百檔已下市的真實紀錄。
回測到過去某年時，universe 要用**當時真的存在的那批**。
`data/stocks/` 已含下市股票，**不要用「今天的清單」去過濾歷史**——那就是生存者偏差。

## 六、讀進來要驗，不要靜默相信

1. **列數**對照 `data/stocks/_index.csv`（`stock_id, rows, first, last`）
2. **日期集合**對照交易日曆 **`data/meta/calendar_twse.csv`**（2,845 天，2015-01-05 起）。
   ⚠ **不要再用 `_coverage_*.csv` 或 `daily/` 的檔名集合當日曆**——
   前者是抓取程式自己記的「我抓到幾列」，後者是被檢查的對象本身，**兩個都是循環自證**：
   某天整批漏抓時它同樣不會出現在日曆裡，覆蓋率反而算出 100%。
   `calendar_twse.csv` 來自 TWSE `FMTQIK`（大盤層級，與建日檔的個股端點不同條路），
   2026-09-07 核對官方 2,845 ＝我方 2,845、兩個方向 0 差異
3. **價格合理性**：`low ≤ open,close ≤ high`、零價與負價、單日漲跌超出 ±11%
   （超出的多半是除權息或資料錯，要點名不要略過）。
   ⚠ 收盤比落在 `< 0.55` 或 `> 1.8` 而 `data/adj/` 沒有對應事件的，**疑似面額變更**——見陷阱 13
4. **大盤方向**：`change` 的正負號與「今日收盤 − 前日收盤」同號（陷阱 8）

**跨管線交叉驗證最有份量**：同一檔若在兩條獨立路徑都有，逐欄比一次。
